# Deploying and running the speech collector on the droplet

This guide covers the DigitalOcean droplet that runs the WhatsApp bot: first-time setup, routine
updates, connecting WhatsApp (Meta Cloud API, plus the Twilio fallback), starting a new collection
run with fresh participants and prompts, testers, backups and rollback. Commands to run **on your
Mac** and **on the droplet** are labelled.

Current setup (replace these if you build a new server):

| What | Value |
|---|---|
| Domain | `bot.zazoai.com` (A record at Hostinger → droplet IP) |
| Droplet IP | `165.227.73.241` |
| Server user | `dun` |
| Repo folder on the droplet | `~/WhatsApp-speech-collector` |
| Participant number (Meta Cloud API) | +1 618-602-0282 (phone number ID `1339556382581787`) |
| Fallback number (Twilio) | +1 941-462-2803 (nyasaAI) |

What runs on the droplet (all in Docker, defined in `docker-compose.yml`):

| Service | What it does | Reachable from the internet? |
|---|---|---|
| `caddy` | HTTPS for the domain (automatic certificates), forwards requests to the API | Yes: ports 80 and 443 |
| `api` | Receives Meta and Twilio webhooks, serves prompt images | No (only through Caddy) |
| `worker` | Stores voice notes, runs the conversation, sends replies | No |
| `migrate` | Updates the database schema, then exits | No |
| `postgres` | The database (data kept in a Docker volume) | No |
| `redis` | The job queue | No |

Files (voice notes, prompt CSVs, images, participant lists) live in `data/` on the droplet, which
the containers share. Settings live in `.env` on the droplet. The design of the collection itself
(task types, targets, QC) is described in `docs/methodology.md`.

## Part A — First-time setup

Done once per server. The current droplet is already set up; keep this for rebuilding.

### A1. Create the droplet

In the DigitalOcean control panel: **Create → Droplets**, Ubuntu 24.04 (LTS) x64, Basic, **4 GB /
2 CPUs** (the image is built on the droplet), authentication with your Mac's SSH key. Optionally
assign a **Reserved IP** (Networking → Reserved IPs) so the address survives rebuilds.

### A2. Point the domain at it (DNS)

At the DNS provider for `zazoai.com` (Hostinger), add an **A** record: name `bot`, value the droplet
IP, TTL 300. Remove any other A/AAAA/ALIAS/CNAME record for the same name. Check on your Mac:

```bash
dig +short bot.zazoai.com @8.8.8.8     # must print only the droplet IP
```

Don't start the app until this is right: Caddy needs it to get the HTTPS certificate.

### A3. Server setup

**On your Mac:** `ssh root@165.227.73.241`. Then **on the droplet** (as root):

```bash
apt update && apt upgrade -y
adduser dun                                   # skip if the user already exists
usermod -aG sudo dun
rsync --archive --chown=dun:dun ~/.ssh /home/dun
ufw allow OpenSSH
ufw allow 80/tcp
ufw allow 443/tcp
ufw allow 443/udp
ufw enable
curl -fsSL https://get.docker.com | sh        # Docker + Compose plugin
usermod -aG docker dun
```

On a 4 GB droplet, add 2 GB of swap for image builds:

```bash
fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
```

Open a **second** terminal and check `ssh dun@165.227.73.241` works before logging out as root.
As `dun`: `docker run --rm hello-world` and `id -u` (note the number: it's `APP_UID`).

> Docker publishes container ports past `ufw`. That's fine here: only Caddy's 80 and 443 are
> published. Postgres and Redis never are.

### A4. Get the code

Commit and push on your Mac first. **On the droplet**, check GitHub access and clone:

```bash
ssh -T git@github.com
git clone git@github.com:dmatekenya/WhatsApp-speech-collector.git ~/WhatsApp-speech-collector
cd ~/WhatsApp-speech-collector
mkdir -p data/participants data/prompts data/audio backups
```

If `ssh -T` is refused, add a read-only **deploy key** (GitHub → repo → Settings → Deploy keys) with
the output of `ssh-keygen -t ed25519 -f ~/.ssh/github_deploy -N "" && cat ~/.ssh/github_deploy.pub`.

### A5. Settings (`.env` on the droplet)

**On your Mac**, build `.env.production` from the template (it copies only the Twilio values from
your local `.env` and generates new secrets; it never prints values):

```bash
python3 scripts/make_env_production.py --dry-run
python3 scripts/make_env_production.py
```

Then fill in by hand: `SUPPORT_CONTACT`, `APP_UID` (from `id -u`) and the Meta values (section B2).
Copy it to the server as `.env`:

```bash
rsync -av .env.production dun@165.227.73.241:~/WhatsApp-speech-collector/.env
ssh dun@165.227.73.241 chmod 600 WhatsApp-speech-collector/.env
```

**Only do this once.** After the first start, edit `.env` **on the droplet** (`nano .env`): the
database password is set when Postgres first starts, and a re-generated file would lock the app
out of its own database.

### A6. Start and import

```bash
cd ~/WhatsApp-speech-collector
./scripts/deploy.sh
docker compose ps        # api, worker, postgres, redis, caddy running; migrate exited (0)
curl -s https://bot.zazoai.com/health
```

Then copy data and import, as described in **Part C** (new collection run).

## Part B — Routine updates and WhatsApp connections

### B1. Updating the code

1. **On your Mac:** run the tests, check nothing private is staged, commit and push:

   ```bash
   uv run pytest -q
   git status          # no .env, .env.production, data/ or backups/ files
   git add -A && git commit -m "..." && git push
   ```

2. **On the droplet:**

   ```bash
   cd ~/WhatsApp-speech-collector
   ./scripts/backup_db.sh                 # always before deploying: migrations may run
   ls -lh backups/ | tail -2              # a new, non-empty .dump file
   git pull
   ./scripts/deploy.sh                    # rebuild, migrate, restart
   ```

   If the update adds new settings, compare with the template and add them to `.env` (on the
   droplet) **before** `deploy.sh`:

   ```bash
   grep -o '^[A-Z_]*=' .env.production.example | sort > /tmp/a
   grep -o '^[A-Z_]*=' .env | sort > /tmp/b
   comm -23 /tmp/a /tmp/b                 # settings in the template but missing from .env
   ```

3. **Check:**

   ```bash
   docker compose ps
   docker compose logs migrate --tail 10  # "Running upgrade ..." lines, no errors
   curl -s https://bot.zazoai.com/health  # {"status":"ok"}
   ```

Settings are read only when the containers start: after any change to `.env` or `config/`,
run `./scripts/deploy.sh` (or `docker compose up -d --force-recreate api worker`).

### B2. Meta WhatsApp Cloud API (participant number)

Settings in the droplet's `.env` (values from Meta; never paste them into chats or screenshots):

```
META_VERIFY_TOKEN=...          # any random string you choose; also entered in Meta
META_APP_SECRET=...            # Meta App Dashboard → App settings → Basic → App secret
META_ACCESS_TOKEN=...          # permanent token of the Admin System User (Business settings)
META_PHONE_NUMBER_ID=1339556382581787
META_WABA_ID=1218633397402517
META_GRAPH_VERSION=v26.0
WHATSAPP_PROVIDER=meta         # default for messages the bot sends without being messaged first
```

Connect the webhook **after** deploying (Meta checks the address immediately):

1. Check the endpoint exists: `curl -s -o /dev/null -w '%{http_code}\n'
   "https://bot.zazoai.com/webhooks/meta?hub.mode=subscribe&hub.verify_token=wrong&hub.challenge=1"`
   prints **403**.
2. Meta App Dashboard (use Chrome) → **Use cases → Customize → Step 2 → Configure Webhooks**:
   callback URL `https://bot.zazoai.com/webhooks/meta`, verify token = `META_VERIFY_TOKEN`,
   **Verify and save**. Subscribe to the **messages** field (optionally `account_update` and
   `phone_number_quality_update`).
3. **Subscribe webhooks** must be on for the WhatsApp account that holds the number (Step 2 →
   Register your WhatsApp phone number).
4. `docker compose logs api --tail 10` shows `Meta webhook verified`.

Token checks (on the droplet, without printing the token):

```bash
set -a; source .env; set +a
curl -s "https://graph.facebook.com/$META_GRAPH_VERSION/$META_PHONE_NUMBER_ID?fields=display_phone_number,verified_name,quality_rating,status" \
  -H "Authorization: Bearer $META_ACCESS_TOKEN"
```

Lessons from setup:

- The System User that owns the token needs the **Admin** role and full control of the app and
  the WhatsApp account; otherwise sending fails with "(#10) Viewer cannot access the provided Paid
  Message Account". Generate a new token after assigning new assets.
- A WhatsApp account created through Twilio can't be used by our app for sending; our number lives
  in our own account ("Zazoai").
- The WhatsApp account needs a payment method, even though replies within 24 hours are free.
- Meta allows **one webhook URL per app**. Never point the production app at ngrok while the pilot
  is running (see B4).

### B3. Twilio (fallback number)

In the Twilio Console → **Messaging → Senders → WhatsApp senders** → +1 941: **When a message comes
in** = `https://bot.zazoai.com/whatsapp/webhook` (POST). Replies always go out on the number the
participant wrote to, so both numbers can run at the same time.

### B4. Local development while the droplet is live

The production Meta app's webhook points at the droplet. For laptop testing, use one of:

- a **separate Meta app** (e.g. "Tiyankhuleni dev") with Meta's free test number, whose webhook
  points at your ngrok URL (`ngrok http --url=ungrayed-ena-seelily.ngrok-free.dev 8000`); or
- the **Twilio sandbox**, with its webhook pointing at ngrok.

Run the laptop app with `uv run uvicorn src.api.main:app --port 8000` and
`uv run rq worker inbound outbound --with-scheduler --worker-class rq.worker.SimpleWorker`, after
`uv run alembic upgrade head`. Your laptop database is separate from the droplet's.

## Part C — Starting a new collection run

Use this for each new group of participants (e.g. a cohort or weekly run), and for the pilot.

### C1. Prepare the files (on your Mac)

| Content | Location | Notes |
|---|---|---|
| Participants | `data/participants/<run>.csv` (e.g. `sr-c01.csv`) | Same columns as `data/participants.example.csv`; phone as `+265 888 72 15 91`; saved as **CSV UTF-8**; `is_test` FALSE for real participants; optional `primary_device_type/brand/model` |
| Sentences | `data/prompts/text/<batch>.csv` | Curated; within the length limits; no sensitive items |
| Conversation starters | `data/prompts/conversation-starters/<batch>.csv` | Chichewa |
| Images | `data/prompts/images/<batch>/<theme>/...` | One folder per theme; JPG/PNG |

Check each file locally first with `--dry-run` (see C4), and fix rejected rows.

### C2. Plan the run (on your Mac)

In `config/assignment_settings.yaml`:

- `targets_minutes.per_participant` — recorded minutes per person for this run (20 for the pilot;
  use a multiple of 20 so every type comes out in whole or half minutes).
- `split` — normally unchanged (30/25/25/20 = 70% spontaneous).
- `task_types.<type>.speakers_per_prompt` — raise it if a type would run out of prompts.

Run the simulation with the planned number of participants and content (it works on a copy of the
database), and check no type runs out ("no prompts for …"):

```bash
uv run python scripts/simulate_task_bank.py --per-participant 20
```

Commit and push any config change.

### C3. Copy the files to the droplet (on your Mac)

```bash
rsync -av \
  --exclude '.DS_Store' --exclude '_prepared/' \
  --exclude '*_imported.csv' --exclude '*_rejected.csv' \
  data/participants data/prompts \
  dun@165.227.73.241:~/WhatsApp-speech-collector/data/
```

Participant CSVs contain names and phone numbers; rsync sends them encrypted over SSH. They are
never committed to git.

### C4. Import on the droplet

```bash
cd ~/WhatsApp-speech-collector
./scripts/backup_db.sh
git pull && ./scripts/deploy.sh        # picks up any config change from C2
```

**Retire content you no longer want assigned** (prompts are never deleted, so history and IDs are
kept; they're just made inactive). For example, to retire the test material:

```bash
docker compose exec postgres psql -U speech -d speech_collector -c \
  "select prompt_type, source_file, count(*) from prompts where active group by 1, 2 order by 1, 2;"
docker compose exec postgres psql -U speech -d speech_collector -c \
  "update prompts set active = false where source_file in ('test-dhs.csv', 'conversation_starters_test_en.csv');"
```

(Use the `source_file` values the first query shows.)

**Import** — always `--dry-run` first, then for real. Run imports in the same order on every
environment so prompt IDs match:

```bash
# Participants
docker compose exec api python -m scripts.import_participants data/participants/<run>.csv --dry-run
docker compose exec api python -m scripts.import_participants data/participants/<run>.csv --write-ids

# Sentences
docker compose exec api python -m scripts.import_prompts sentences data/prompts/text/<batch>.csv --dry-run
docker compose exec api python -m scripts.import_prompts sentences data/prompts/text/<batch>.csv --write-ids

# Conversation starters
docker compose exec api python -m scripts.import_prompts conversation_starters \
  data/prompts/conversation-starters/<batch>.csv --write-ids

# Images (prepared WhatsApp copies are made here, on the server)
docker compose exec api python -m scripts.import_prompts images data/prompts/images/<batch> \
  --source ai-generated --write-ids
```

Each import ends with `RESULT: imported` and reports any rejected rows.

**Check what's active now:**

```bash
docker compose exec postgres psql -U speech -d speech_collector -c \
  "select prompt_type, count(*) filter (where active) as active, count(*) as total from prompts group by 1;"
docker compose exec postgres psql -U speech -d speech_collector -c \
  "select participant_id, is_test, status, batch from participants order by participant_id;"
```

**Close the previous run** (optional): participants from an earlier run who should no longer
record can be set to `completed` so the bot stops giving them tasks:

```bash
docker compose exec postgres psql -U speech -d speech_collector -c \
  "update participants set status = 'completed' where batch = '<previous-run>.csv';"
```

### C5. Smoke test and launch

1. From your phone (a test participant), send **Hi** to +1 618-602-0282: the summary shows the run's
   target (e.g. 20 minutes, four lines). Record one clip.
2. Check: `docker compose logs -f api worker`, and

   ```bash
   docker compose exec postgres psql -U speech -d speech_collector -c \
     "select id, channel, status from outbound_messages order by id desc limit 3;"   # meta, delivered/read
   ```

3. Brief participants: save **+1 618-602-0282**, send **Hi** to start, contact for problems.

### C6. During the run

```bash
docker compose logs -f api worker                        # live activity
docker compose exec postgres psql -U speech -d speech_collector -c \
  "select status, count(*) from outbound_messages where created_at > now() - interval '1 day' group by 1;"
docker compose exec postgres psql -U speech -d speech_collector -c \
  "select qc_status, qc_reason, count(*) from recordings where created_at > now() - interval '1 day' group by 1, 2;"
```

`failed` or `skipped_window` outbound messages, or many `too_short` / `too_long` / `not_recorded`
recordings, are worth a closer look.

## Part D — Testers and support

### D1. Adding a tester

Testers are ordinary participants with `is_test` TRUE (excluded from exports). Add them to a small
CSV (e.g. `data/participants/testers.csv`), copy and import it as in C3–C4. Give a tester a short
target so they reach every task quickly:

```bash
docker compose exec postgres psql -U speech -d speech_collector -c \
  "update participants set attributes = jsonb_set(coalesce(attributes,'{}'::jsonb), '{targets_minutes}', '{\"per_participant\": 4}') where participant_id = 'P00XX';"
```

Remove it afterwards: `... set attributes = attributes - 'targets_minutes' where participant_id = 'P00XX';`

### D2. Resetting a stuck participant

Closes their open session, releases unanswered prompts and resets the conversation; recordings and
progress are kept:

```bash
docker compose exec api python -m scripts.reset_participant P00XX --dry-run
docker compose exec api python -m scripts.reset_participant P00XX
```

Without the script, the same by hand:

```bash
docker compose exec postgres psql -U speech -d speech_collector -c "update sessions set status = 'abandoned', ended_at = now() where participant_id = 'P00XX' and status in ('active','paused');"
docker compose exec postgres psql -U speech -d speech_collector -c "update assignments set status = 'expired' where participant_id = 'P00XX' and status = 'sent';"
docker compose exec postgres psql -U speech -d speech_collector -c "update conversation_state set state = 'idle' where participant_id = 'P00XX';"
```

## Part E — Backups, rollback and restore

### E1. Backups

`scripts/backup_db.sh` saves the database to `backups/speech_collector_YYYY-MM-DD_HHMMSS.dump` and
keeps the newest 14. Schedule it nightly (`crontab -e`):

```
30 2 * * * /home/dun/WhatsApp-speech-collector/scripts/backup_db.sh >> /home/dun/WhatsApp-speech-collector/backups/backup.log 2>&1
```

The dump doesn't include audio. Keep copies off the server (**on your Mac**):

```bash
rsync -av dun@165.227.73.241:~/WhatsApp-speech-collector/backups/ ~/speech-collector-backups/
rsync -av dun@165.227.73.241:~/WhatsApp-speech-collector/data/audio/ ~/speech-collector-audio/
```

Both contain personal data: keep them on an encrypted disk.

### E2. Rolling back a bad update

```bash
cd ~/WhatsApp-speech-collector
git log --oneline -5
git checkout <previous-good-commit>
./scripts/deploy.sh
```

Return to the latest code later with `git checkout main && git pull`. If the bad update ran a
migration that damaged data, also restore the backup taken before it (E3).

### E3. Restoring a backup

Replaces the current database:

```bash
cd ~/WhatsApp-speech-collector
docker compose stop api worker
docker compose exec -T postgres sh -c 'pg_restore --clean --if-exists --no-owner -U "$POSTGRES_USER" -d "$POSTGRES_DB"' \
  < backups/speech_collector_2026-11-05_195000.dump
docker compose start api worker
```

## Part F — Troubleshooting

| Symptom | Likely cause | Check / fix |
|---|---|---|
| WhatsApp shows *delivered* but nothing in the API log | Meta isn't sending to the droplet | Webhook URL and **messages** subscription in Meta; **Subscribe webhooks** on for the WhatsApp account |
| API log: "Meta message for a different phone number ID ignored" | Message sent to another number on the app | Expected for +1 941; otherwise check `META_PHONE_NUMBER_ID` and restart |
| Webhook POSTs get 403 | App secret mismatch | `META_APP_SECRET` = Meta App settings → Basic; restart |
| Replies `failed`, error `(#10)` | Token's System User lacks rights | Admin role, full control of app and WhatsApp account, new token |
| Replies `skipped_window` | Participant's last message > 23.5 h ago | Expected; they need to message first |
| Worker errors "column ... does not exist" | Migration not applied | `./scripts/deploy.sh` (droplet) or `uv run alembic upgrade head` (laptop) |
| Old settings still in effect | Containers not restarted | `./scripts/deploy.sh` |
| HTTPS fails | DNS or ports | `dig +short bot.zazoai.com @8.8.8.8`; `docker compose restart caddy` |
| Images don't arrive | Meta can't fetch the image URL | `PUBLIC_BASE_URL=https://bot.zazoai.com`; `docker compose logs caddy` |
| Meta dashboard won't load or blocks actions | Browser or new-device checks | Use Chrome; wait out "new device" timers instead of retrying |
